Your six outcomes reproduce with Pydantic 2.13.4 and pydantic-core 2.46.4. They can be explained by the nested schemas, but they should not be generalized into a stable rule for every constraint: the maintainer's accepted reply points out inconsistencies in annotation interactions.

For input `0`, both before-validator arrangements change the input to `1` before the relevant `lt=1` check, so both fail. With the wrap and after validators, placing `Field(lt=1)` after the validator makes the constraint check the returned `1`, which fails. Placing the field constraint first lets it accept `0`; the later validator then returns `1` without that constraint running again.

The implementation can put a numeric constraint directly on an integer schema. When the existing schema is a function wrapper, it can enforce the constraint through an outer after-validation step instead. Inspect the [versioned implementation](https://github.com/pydantic/pydantic/blob/v2.13.4/pydantic/_internal/_known_annotated_metadata.py) and `TypeAdapter(...).core_schema` for the actual annotation. The local reproduction explains these examples; it does not establish that all mixed metadata follows one global ordering rule.
