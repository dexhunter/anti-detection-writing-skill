Create the redirect, set its cookie, and return that same `RedirectResponse`:

```python
@app.get("/cookiefail")
def cookie_fail():
    response = RedirectResponse("/")
    response.set_cookie(key="works", value="here is your data")
    return response
```

The injected `Response` is a separate object. FastAPI copies its headers when building a response from ordinary returned data; returning a response instance skips that step.

This [documented approach](https://fastapi.tiangolo.com/advanced/response-cookies/#return-a-response-directly) needs neither `response_class=RedirectResponse` nor a hard-coded cookie domain. Leaving the domain unset avoids tying the example to `127.0.0.1`, though normal cookie matching rules still apply. Cookies are separate from localStorage.

The newer `/authorize` example already sets the cookie on the returned redirect, so it needs further diagnosis. Check the redirect's `Set-Cookie` header, the following request's `Cookie` header, the actual hosts, and the test client's cookie handling before assigning a cause. The browser behavior has not been reproduced here.
